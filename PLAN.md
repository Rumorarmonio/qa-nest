# План реализации

## Проект

QA Backend - учебный backend на NestJS + Prisma + PostgreSQL для сценария вопросов и ответов с JWT-аутентификацией, ролями USER/ADMIN, CRUD для questions/answers, сидерами, Swagger, тестовой инфраструктурой и планируемой админкой.

## Цель

Довести backend/API до устойчивого MVP: закрыть критичные вопросы авторизации и прав доступа, зафиксировать бизнес-инварианты на уровне сервиса и БД, покрыть важные сценарии тестами, затем подключить админку. После этого можно переходить к frontend-контрактам и самому frontend.

## Этапы

1. Стабилизировать API и модель данных: ownership rules для вопросов и ответов; правила удаления answers; constraint на единственный best answer в Postgres; тесты на auth, roles и бизнес-логику; при необходимости уточнение поведения ошибок и статусов.
2. Подключить админку: доступ только для ADMIN; ресурсы User, Question, Answer; скрытие чувствительных полей; базовые действия модерации и управления контентом; минимальный набор экранов без лишнего scope.
3. Расширять продукт после стабилизации backend: поиск и фильтрация вопросов, теги/категории, комментарии, лайки, уведомления, затем frontend-контракты и frontend-приложение.

## Статус этапов

- Этап 1 — в процессе: ownership rules для update questions/answers зафиксированы в сервисах и покрыты тестами; тестовые helpers переведены на фабрики; e2e helper-слой собран в единый `createE2eHelpers`; integration-тесты получили `setupIntegration`; для integration/e2e добавлена отдельная test DB через `.env.test` и `postgres-test` в docker-compose, тесты запускаются последовательно через `--runInBand`; `db:test:reset` теперь также сидит базовых пользователей для e2e; добавлены проверки `best answer` при создании ответа с `isBest=true` и на DB-level unique constraint; в текущей среде Docker DB недоступна, поэтому sequential verification надо повторить после поднятия `postgres-test`
- Этап 2 — не начат
- Этап 3 — не начат

## Следующий этап

Завершить остатки этапа 1: повторно прогнать integration/e2e на поднятой test DB, затем убедиться, что sequential workflow стабилен с seed users, и после этого перейти к минимальному scope админки.

## Минимальный scope админки

Первая версия админки должна быть узкой и практичной:

- Доступ только для `ADMIN`.
- Отдельный backoffice поверх существующего API, без замены Adminer.
- Ресурсы: `User`, `Question`, `Answer`.
- Для `User`: список, просмотр карточки, смена роли `USER/ADMIN`.
- Для `Question`: список, просмотр, удаление, базовая модерация.
- Для `Answer`: список, просмотр, удаление, управление `isBest` при необходимости модерации.
- В выдаче скрывать чувствительные поля вроде `passwordHash` и любые служебные токены.
- Для списков оставить только минимально нужные поля: `id`, краткое описание/превью, автор, `createdAt`, необходимые флаги статуса.
- Фильтры первой версии: `id`, автор, роль пользователя, `isBest`, дата создания.
- Не включать в первую версию дашборды, массовые операции, историю модерации, сложные workflow, audit log и soft delete, если они не нужны для запуска.
