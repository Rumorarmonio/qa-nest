# План реализации

## Проект

QA Backend - учебный backend на NestJS + Prisma + PostgreSQL для сценария вопросов и ответов с JWT-аутентификацией, ролями USER/ADMIN, CRUD для questions/answers, сидерами, Swagger, тестовой инфраструктурой и планируемой админкой.

## Цель

Довести backend/API до устойчивого MVP: закрыть критичные вопросы авторизации и прав доступа, зафиксировать бизнес-инварианты на уровне сервиса и БД, покрыть важные сценарии тестами, затем подключить админку. После этого можно переходить к frontend-контрактам и самому frontend.

## Этапы

1. Стабилизировать API и модель данных: ownership rules для вопросов и ответов; правила удаления answers; constraint на единственный best answer в Postgres; тесты на auth, roles и бизнес-логику; при необходимости уточнение поведения ошибок и статусов.
2. Подключить админку: доступ только для ADMIN; ресурсы User, Question, Answer; скрытие чувствительных полей; базовые действия модерации и управления контентом; минимальный набор экранов без лишнего scope.
3. Расширять продукт после стабилизации backend: поиск и фильтрация вопросов, теги/категории, комментарии, лайки, уведомления, затем frontend-контракты и frontend-приложение.

## Статус этапов

- Этап 1 — завершён: ownership rules для update questions/answers зафиксированы в сервисах и покрыты тестами; тестовые helpers переведены на фабрики; e2e helper-слой собран в единый `createE2eHelpers`; integration-тесты получили `setupIntegration`; для integration/e2e добавлена отдельная test DB через `.env.test` и `postgres-test` в docker-compose, тесты запускаются последовательно через `--runInBand`; `db:test:reset` теперь также сидит базовых пользователей для e2e; добавлены проверки `best answer` при создании ответа с `isBest=true` и на DB-level unique constraint; sequential verification подтверждена пользователем
- Этап 2 — в процессе: AdminJS подключён поверх существующего API как готовая админка; ui-монтаж и auth для `/admin` уже заведены, сессии вынесены в Postgres, обязательные env-секреты для админки явно проверяются, а дефолтная dark theme и toggle переключения dark/light уже добавлены; ручной запуск всё ещё требует доступной Postgres на `127.0.0.1:5432`
- Этап 3 — не начат

## Следующий этап

Поднять Postgres и вручную проверить `/admin` с заданными `ADMINJS_COOKIE_PASSWORD` и `ADMINJS_SESSION_SECRET`, затем убедиться, что dark/light переключаются через toggle в шапке и сохраняются в session.

## Минимальный scope админки

Первая версия админки должна быть узкой и практичной:

- Доступ только для `ADMIN`.
- Отдельный backoffice поверх существующего API, без замены Adminer.
- Не добавлять отдельные `/admin` read-endpoints без явной необходимости.
- Использовать готовую админку вместо собственного frontend для первой версии.
- AdminJS — текущий выбор для первой реализации админки.
- `User`-управление отложить до появления явной необходимости.
- Админский scope ограничить тем, что реально отличается от обычного пользователя: дополнительные write-actions, если они понадобятся, и более широкие права доступа там, где это оправдано.
- Не включать в первую версию дашборды, массовые операции, историю модерации, сложные workflow, audit log и soft delete, если они не нужны для запуска.

## Порядок реализации админки

1. Подключить AdminJS как готовую админку поверх существующего API и Prisma.
2. Проверить, достаточно ли стандартного AdminJS UI без кастомных endpoints.
3. Если после этого останутся реальные gap'ы, добавить только точечные кастомные actions.
4. Обновить Swagger/OpenAPI и при необходимости README с описанием админского поведения.
